# 簡化改版差距分析（2026-10-09；2026-10-11 更新至 Build 13）

依據 `CodexWorkResumer_SPEC_zhTW.md` 與 `CodexWorkResumer_UI_Mockup.html`，對照既有 Go watchdog、官方 Codex app-server、PowerShell WinForms 主畫面及 Windows 系統匣。HTML 是資訊層次示意，不是改用網頁技術的指令。

## 已具備

- 同一個 Go watchdog 有單一 `daemon` 排程 tick、每 Task 的 Pending／Awaiting／Stopped 狀態、同 Task 防重複與跨 Task 啟動間隔；網路、逾時等暫時故障自動救援必須保留。
- Codex Task 以穩定的 thread ID 識別；清單可從官方 `thread/list`、`thread/turns/list` 讀取近期 Task 的標題、工作目錄與最新 turn 狀態。Resume 優先使用正式 IPC；CLI 備援只有使用者明確啟用才使用。
- 額度以唯讀 `account/rateLimits/read` 為主，顯示 5H／Weekly 剩餘比例與 reset 倒數；配額門檻會在派送前重查。預設刷新為 1 分鐘，並非規格範例中的 5 分鐘。
- 主畫面已能重新整理 Task 清單、設定 60 秒自動掃描與 30 秒跨 Task Resume 間隔；暫停狀態和大部分重試設定已有持久化。

## 這次先修的實際故障

2026-10-08 的安全診斷紀錄顯示 Codex 回傳 `codex_error_info=usage_limit_exceeded`。rollout 事件解析原本沒有保留這個結構化代碼，文字分類器也不認得「usage limit」，導致先排入 `unknown` 快速重試；catalog 的另一條路徑稍後才辨識 `rate_limit`。同一 Task 的 catalog 命令還可能把既有 Pending 截止時間提前。修正方向是統一辨識額度代碼、讓既有額度等待不被第二條發現路徑催促，並保留新鮮額度預檢。

官方額度百分比可能與剛發生的 provider 額度拒絕不一致（例如畫面仍顯示 10%）。這種衝突不能直接視為可用；新版先等最近的 reset 時點，再讀取正式額度資料。系統匣不再僅憑正百分比把已排定的等待提前改成立即續跑。這是保守策略：若額度其實提前恢復，本版可能仍等到 reset，後續須有可驗證的額度變化證據才能安全提早喚醒。

Task 名稱不是無法取得：catalog 有正式標題，但 Pending／Awaiting／Stopped 覆蓋列原本用專案資料夾名及短 ID 取代它；而超出最近 10 筆的恢復項目根本不在 catalog 裡。修正後合併時保留官方標題與路徑，較舊的恢復項目另以官方 `thread/read` 依 ID 補讀；若本機 app-server 不回傳名稱，仍顯示明確的 fallback，不假裝已取得 UI 標題。

主程式內建 Mini Monitor 不是獨立程式，與 watchdog 共用程序及設定。依使用者最新指示，從主程式移除它的視窗、設定頁籤及系統匣入口；主畫面額度區、Task 清單、自動續跑、系統匣狀態都保留。舊 `mini-monitor.json` 使用者資料不刪除；獨立 Mini Monitor 由另一個開發對話完成，不能把本次移除誤稱為獨立版已交付。

## 規格分階段進度（Build 13 原始碼）

| 項目 | 現有狀況與最小安全路徑 |
| --- | --- |
| 執行中預先勾選 | Build 10 已將勾選改為額度監控選取，執行中也可勾；不立即 Resume。手動 Resume 改用反白列。選取以 thread ID 獨立持久化；未建立名單的舊版使用者仍沿用全部額度故障自動救援，畫面明示此例外。 |
| 拖曳排序與重開還原 | Build 10 已保存同一份可見順序；額度恢復後的下一個合格候選依該順序派送。點欄標題仍可暫時排序檢視，拖曳後回到排程順序。多視窗修改採修訂版衝突保護；未勾選的舊項目才可因 100 項上限淘汰。 |
| 循序／間隔兩模式 | 在原有 `daemon` 唯一派送入口使用 `staggered_start`（預設）與 `sequential_completion`，只約束額度續跑，不改暫時故障救援。前者依 30 秒啟動間隔與可觀測執行上限安排下一個候選；後者保留目前 owner，直到可觀測的正向完成經後續健康掃描確認，或明確中止、無須續跑、停止情境安全釋放。沒有第二個 scheduler。 |
| 額度輪詢 | 現為每 1 分鐘，使用者已指定保留此預設；規格 5 分鐘視為舊示意值。只有可信的配額耗盡才進入預選排程；既有暫時故障救援仍保留原政策。 |
| 停止／續跑結果 | 單憑暫時閒置或一筆 `turn/completed` 不宣稱整個 Task 已完成。循序持有者的正向完成需安靜期與後續完整掃描確認才交棒；明確中止／無須續跑也待健康掃描後交棒，重試已停止則直接讓出位置但保留監控勾選。額度暫停、Goal 尚未完成與未知狀態繼續等待。畫面將已停止重試、監控勾選與可確認的同 Task 續跑成功區分，成功只代表本回合結束。 |

| 四個主畫面分區 | 沿用 PowerShell WinForms，在總覽同一捲動頁整理為 01 監控與操作、02 Session 清單與執行順序、03 排程模式與參數、04 通知與執行紀錄；原有設定／狀態說明／診斷分頁仍保留。HTML 只作資訊層次參考。 |

## 已確認取捨與驗證邊界

- 使用者確認保留既有暫時故障自動救援；Build 10 預選及 Build 11 雙模式只約束額度故障，自動派送仍經既有 `daemon` 出口。一次性人工重新排隊尚未交付。
- 不以無輸出時長推定工作卡住；不把 Resume 當額度探針；不因未知錯誤自動重試到無限次。
- 只有 Codex 原生 Goal 明確完成能宣告原生目標完成；一般回合的正向完成加安靜期與掃描，只用於排程交棒，不宣告整個專案工作完成。也未證明能完整計算所有外部人工啟動的工作。
- 目前已安裝 Build 12；Build 13 的原始碼、隔離測試與發行包不會自動替換安裝版。使用者安排安全升級後才會在正式程式看到變更。
- Build 11 的原始碼另修正兩項問題：MSIX 共享路徑直接啟動遭 Windows 拒絕時，安全啟動器改用官方套件入口並標示未建立共享通道；主畫面額度警告只統計正在等待額度的有效項目，不再由歷史／停止項目觸發。這些來源層修正尚不等於本機安裝版已更新，也不等於完成實機驗收。
- Build 11 更新管理面板的 npm 建置相依套件。本次正式執行相依套件 `npm audit --omit=dev` 為 0 項弱點；完整開發相依套件仍有 3 項 high，集中在 `vite-plugin-singlefile` 的建置鏈，未以可能破壞相容性的強制降版掩蓋。Go、TypeScript、PowerShell 隔離測試與發行 ZIP 驗證均已執行；這不等於正式安裝後的真實 Codex 續跑驗收。

## 下一個安全驗證順序

1. Build 13 的本機建置、隔離啟動與 ZIP 完整性驗證完成後，由使用者安排不干擾現有工作的升級時間；若舊共享通道仍連接 Codex，安裝程式會要求先關閉 Codex。
2. 正式安裝後，檢查四區畫面、安全啟動器官方備援提示、歷史額度警告不再誤報，以及已停止監控與續跑成功的明確狀態。
3. 以真實額度耗盡、reset 後原 Task 續跑及兩種模式的順序驗收；隔離測試不能證明真實工作已成功續跑。ChatGPT Work 續跑仍沒有已驗證的正式通道，本版未支援。
